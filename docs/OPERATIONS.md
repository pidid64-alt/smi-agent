# Эксплуатация

## 1. Развёртывание
**Один узел (SQLite), без Docker:**
```bash
pip install .
cp .env.example .env            # заполнить; ключи: smi-agent keys generate
export $(grep -v '^#' .env | xargs)   # или systemd EnvironmentFile
smi-agent init --admin admin --project main
smi-agent serve --host 127.0.0.1 --port 8000     # + обратный прокси с TLS
smi-agent worker                                  # либо SMI_EMBEDDED_WORKER=1
```
**Windows (один узел, SQLite, без Docker):** пошаговая инструкция — в README, «Запуск на Windows». Кратко: `py -m venv .venv`, `.\.venv\Scripts\python -m pip install .`, файл `.env` в UTF-8 (программа читает его сама — `export $(…)` не нужен), затем `smi-agent init`, `smi-agent serve` и `smi-agent worker` (или `SMI_EMBEDDED_WORKER=1`). Особенности:
- папки `data\` и `backups\` — на локальном диске вне OneDrive/Dropbox и сетевых папок (SQLite в режиме WAL на них работает ненадёжно);
- восстановление из копии (`smi-agent backup restore … --target …`) — **только при остановленном сервере**: открытые файлы БД на Windows нельзя заменить или удалить;
- автозапуск (не проверялся): Планировщик заданий — триггер «При запуске компьютера», действие `…\.venv\Scripts\smi-agent.exe` с аргументом `serve`, «Рабочая папка» — каталог с `.env`; либо оформить службой сторонним инструментом (например, NSSM);
- production на Windows не проверялся (HTTPS-прокси, MFA, автозапуск): для него рекомендуются Linux и Docker.

**Docker:** `docker compose up -d --build` (профиль `tls` добавляет Caddy с автоматическим HTTPS, профиль `pg` — PostgreSQL). Файлы написаны по документации; в среде разработки Docker не запускался — проверьте сборку на своей инфраструктуре.

Обязательно в production: `SMI_ENV=production`, `SMI_PUBLIC_URL=https://…`, `SMI_MASTER_KEYS`, `SMI_BACKUP_KEY`; приложение при неверной конфигурации предупреждает в «Система → Состояние → config» (и не стартует без мастер-ключа). Перечень переменных — в `.env.example`.

## 2. Фоновые задания (`smi-agent worker`)
Задания защищены арендой (`job_leases`): можно запускать несколько воркеров, одно задание выполняется одним из них.

| Задание | Интервал | Что делает |
|---|---|---|
| `publish` | 20 с | публикует наступившие запланированные посты (атомарный захват) |
| `recover` | 2 мин | сверка зависших в «Публикуется» |
| `monitor` | 1 мин | опрос источников (по интервалам источников), кластеризация, оценка |
| `funnel` | 2 ч | запуск воронки → новые 5 предложений |
| `autopilot` | 5 мин | цикл автопилота / со-редактора |
| `metrics` | 30 мин | метрики публикаций, оценка результата, аудитория |
| `backup` | `SMI_BACKUP_INTERVAL_MIN` (15) | шифрованная копия (+проверка примерно раз в час) |
| `health` | 1 мин | проверка компонентов, оповещения при ухудшении |
| `reports` | 1 ч | недельный отчёт (пн ≥08:00) и месячный (1–3 число) |
| `audit_verify` | сутки | проверка хеш-цепочки журнала |
| `cleanup` | сутки | просроченные сессии, попытки входа, старые записи здоровья/LLM |

## 3. Мониторинг
* `GET /api/health/live` — без авторизации (для балансировщика), `GET /api/health` — подробно (сессия/токен), `GET /api/metrics` — Prometheus (`smi_component_status{component=…}` 0/1/2, `smi_overall_status`; суперадмин или сервисный токен).
* Компоненты: `database, sources, worker, publishing, accounts, llm, backup, disk, audit_chain, killswitch, config`. Пороги: обязательный источник (NUR.KZ) не работает → `fail`; ≥30% источников — `warn`; просрочено публикаций → `fail`; копия старше 3 интервалов → `warn`; свободного места <10% → `warn`, <3% → `fail`.
* Оповещения при ухудшении — в интерфейсе («Система → Оповещения») и в `notifications`; внешней доставки (e-mail/мессенджер) нет — подключите Prometheus Alertmanager/Uptime-монитор к эндпоинтам.
* Логи — в stdout (`SMI_LOG_LEVEL`), секреты маскируются.

## 4. Резервные копии, RPO и RTO
* Копия = консистентный онлайн-снимок SQLite (`sqlite3.backup`) → gzip → AES-256-GCM (ключ `SMI_BACKUP_KEY`, **отдельный** от мастер-ключа) → `SMI_BACKUP_DIR` (права 0600) + запись в `backup_records` (SHA-256, размер). Рядом кладётся журнал отзывов `revocations.jsonl`.
* **RPO** = интервал копирования (по умолчанию **15 минут**; хранится `SMI_BACKUP_RETENTION`=96 копий ≈ 24 ч плюс последняя проверенная). Для меньшего RPO уменьшите интервал или используйте PostgreSQL с WAL-архивацией.
* **RTO** измеряется командой `smi-agent backup restore-test` (или кнопкой «Проверить восстановление»): расшифровка → распаковка → проверка целостности SQLite и хеш-цепочки аудита; на демо-данных — доли секунды; на вашем объёме запишите фактическое значение. Целевой RTO документируется как «время restore-test + запуск приложения».
* Хранение: копируйте каталог копий **вне сервера** (другой носитель/облако); ключ `SMI_BACKUP_KEY` храните отдельно от копий.

**Восстановление:**
1. Остановите приложение и воркер.
2. `smi-agent backup list` → выберите копию; `smi-agent backup verify <путь>`.
3. `smi-agent backup restore <путь> --target /data/smi_agent.db --force` (старый файл сохранится как `.bak`).
4. Команда сама **переприменяет журнал отзывов**: секреты и аккаунты, отозванные после копии, останутся отозванными.
5. Запустите приложение; проверьте «Система → Состояние» и `smi-agent audit-verify`; перевыпустите токены платформ, отозванные в период после копии (если требуется).

## 5. Ротация ключей
1. `smi-agent keys generate` → добавьте новый ключ **первым** в `SMI_MASTER_KEYS` через запятую (старый оставьте).
2. Перезапустите процессы; выполните `smi-agent keys rotate` (перешифрует секреты новым ключом, запишет в аудит).
3. Через срок хранения копий удалите старый ключ. Для `SMI_BACKUP_KEY`: новый ключ действует для новых копий; старые копии расшифровываются только старым ключом — храните его, пока копии нужны.

## 6. PostgreSQL
`pip install ".[postgres]"`, `SMI_DATABASE_URL=postgresql+psycopg://…`. Код использует стандартные возможности SQLAlchemy, блокировки строк (`FOR UPDATE`) и триггеры журнала аудита для PostgreSQL. **Не запускался в среде разработки** — выполните полный набор тестов и проверку на стенде до продакшена (тесты используют SQLite). Копии для PostgreSQL делаются через `pg_dump` (нужен клиент), для продакшена лучше WAL-архивация/pgBackRest. Версионных миграций нет: схема создаётся `create_all`.

## 7. Регламенты (runbooks)
| Ситуация | Действия |
|---|---|
| **Публикация «Ошибка» с неизвестным исходом** | не повторять вслепую. «Сверка»: Instagram/Facebook найдут пост сами; Telegram — проверьте канал вручную и нажмите «Уже опубликовано» либо «Повторить» с подтверждением, что поста нет (решение пишется в аудит) |
| **Автопилот опубликовал не то / подозрение на сбой** | красная кнопка «ОСТАНОВИТЬ АВТОПИЛОТ» (любой пользователь), разберитесь, снимет администратор; запланированные посты автопилота вернутся в «Ожидает подтверждения» |
| **Аккаунт «нужна повторная авторизация»** | «Управление → Аккаунты → Новый токен»; проверка подключения выполнится автоматически |
| **Утечка токена** | «Отозвать» аккаунт (токен уничтожается), выпустите новый на стороне платформы, подключите заново; проверьте «Журнал аудита» |
| **Лента источника устарела/ошибки** | «Система → Источники» (статус, последний результат); проверьте адрес, при необходимости отключите источник; NUR.KZ отключается только с подтверждением |
| **Нарушение цепочки аудита** | `smi-agent audit-verify` покажет первую испорченную запись; остановите запись, сделайте копию, расследуйте доступ к БД; восстановление — из проверенной копии |
| **Закончился дневной бюджет LLM** | тексты автоматически уходят в заготовки (автопилот не публикует); увеличьте `SMI_LLM_DAILY_CALL_BUDGET` или дождитесь следующих суток |
| **Мало места на диске** | проверьте `backups/` и `media/`; уменьшите `SMI_BACKUP_RETENTION`; старые метрики/здоровье очищаются заданием `cleanup` |
| **Смена пароля администратора** | `smi-agent user reset-password --username …` (сессии отзываются) |
